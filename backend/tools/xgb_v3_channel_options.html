XGB v3 — Step B.1 channel signal options

Brainstorming doc · branch feat/gpu-coord-mirror · 2026-05-17

Status: Pre-design brainstorm. No code changes proposed yet. Goal of Step B.1 = give the XGB v3 extractor distinct per-channel signal data (it currently sees the same close stats across all 28 channel slots). XGB-side only — CNN is frozen.

Current state of v3

The v3 extractor in backend/tools/xgb_features.py:216 takes a tier dict and produces 350 feature names. What it actually does:

candles_by_tier = {
    "micro": [last 60 hourly candles],   # each candle = OHLCV dict
    "meso":  [last 168 hourly candles],
    "macro": [last 336 hourly candles],
}

# For EVERY channel c in 0..27:
#   _stats_from_candles(candles, ...) uses candles[i]["close"] only
#   → produces 10 stats: last, mean, std, slope, min, max, pct_rank, dlt5, dlt10, dlt30
#
# Result: 28 "channels" × identical close-derived stats
#         dressed up with chN_ name prefixes.

So out of 350 named features, only ~30 carry distinct information (10 stats × 3 tiers). The other 320 names are duplicates the booster splits on independently but which carry the same underlying signal. The booster wastes capacity learning that ch0_last == ch1_last == … == ch16_last.

Option A — OHLCV per-channel RECOMMENDED

5 channels: open, high, low, close, volume

surgical

Each channel carries one of the five raw OHLCV streams. XGB's gradient boosting handles its own feature engineering via tree splits — we just give it diverse raw input.

N_CHANNELS = 5 ~250 features retrain required ~1-2 days impl
  • Smallest, cleanest contract. No "what indicator should we use" debate.
  • XGB splits handle non-linear combinations (it's a tree learner — it doesn't need pre-computed RSI to find RSI-like patterns).
  • Volume is the cheapest new signal we're not using and is in every candle row already.
  • Step B.2 (marketcap) slots in cleanly as channels 5 and 6.
  • Fewer features means less booster capacity to work with — may underfit if 250 isn't enough for the 200-tree budget.
  • Drops the channel-naming back-compat with CNN's 28 (cosmetic break only — XGB has its own checkpoint anyway).

12 channels: hand-picked TA indicators

N_CHANNELS = 12 ~540 features retrain required ~3-5 days impl requires signal-design research
  • Each channel is interpretable — easy to ablate, easy to explain a decision.
  • Bounded normalized values play well with tree split thresholds.
  • Closer to how a discretionary trader thinks (RSI overbought, MACD divergence).
  • "Which 12 indicators" is its own multi-iteration decision — needs research/probes to validate the set.
  • Each indicator is a new piece of compute to write + test. ~12 small functions, each with edge cases.
  • XGB can derive most of these from OHLCV via splits — pre-computing them is partial double-work.
  • Step B.2 marketcap wiring needs its own channel-idx allocation (12 → 14).

Option C — Keep N_CHANNELS=28, expand to distinct signals

28 distinct signals reusing current channel slot indices

heavy

Preserve the channel layout (28 slots, MESO_CHANNELS={15,24,25,26}, MACRO_CHANNELS={20,21,27}, masked {17,18,19}) and feature-name count (350), but compute distinct signals for each slot independently — XGB-side. This is the option most aligned with the original CHANGELOG description of Step B.1, but it's the largest scope.

  • Zero-change to N_CHANNELS, feature_set name, tier-set constants — calibrator pickle metadata stays compatible (shape-wise).
  • Preserves the operator's mental model from existing Module 4a/4b memory.
  • If we later cap channels at <28 for performance, infrastructure already handles that via masked slots.
  • 28 signal definitions to design AND defend — most expensive scope.
  • Half the slots end up being trivial variations (open/high/low ≈ close + small offset) — diminishing returns.
  • Step B.2 marketcap needs to either expand to N=30 (breaks the "preserve 28" promise) OR replace an existing channel (which one?).

Decision rubric

Three lenses to pick by:

If you want to ship fast & test the hypothesis

Pick Option A. Tiny scope, low risk, retrains cheaply. If "give XGB more diverse channel data" lifts AUC, A will show it. If A doesn't help, B and C probably won't either.

If interpretability matters for trade triage

Pick Option B. Each channel name maps to a well-known trader concept. When XGB flips a decision, you can explain it by which indicator changed.

If the operator wants to preserve N_CHANNELS=28 cosmetics

Pick Option C. Most expensive. Only worth it if there's an external reason to keep the 28-slot shape (e.g., shared schema with another consumer).

My recommendation: Option A. Smallest commit, fastest retrain feedback, cleanest Step B.2 slot. If A's booster AUC underperforms current v3, escalate to B.
